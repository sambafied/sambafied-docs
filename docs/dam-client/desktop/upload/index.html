Import files, publish changes and inspect history

Guide home · Coverage and gaps · Image plan

Development guide draft, reviewed 28 October 2026. Steps describe the approved contract and are conditional on the installed build advertising that capability. Product and target acceptance remain separate.

There are two publication intentions: add a new remote asset, or upload a saved generation of an existing asset. Review the destination, account and generation for both. Before a large import, inspect names and hierarchy rather than treating every local file as eligible. Manual publication is the baseline; an automatic policy is separately opted into and bounded to reviewed generations.

History and version expectations​

Upload acknowledgement, binary commit, processing, version creation and check-in are distinct milestones. Use the retained operation and supported history view to establish what happened. Server capability determines whether labels/comments and history preservation are available. Do not claim that upload automatically unlocks the asset or that a processing failure means the bytes never committed.

W12​

Add new files​

Documentation: FULL. Before you start: Have destination write permission and ordinary source files outside the managed source tree.

Procedure. Choose Upload File or the local-only import route. Select sources and the destination. Inspect names, sizes, collisions and the immutable source snapshot review. Approve only the reviewed files and follow their transfer records.

Expected result. New-asset import is distinct from updating a managed asset. Picking a file does not authorize silently replacing another asset.

Cancel, errors and recovery. Picker Cancel is a no-op. If the source changes during capture, or cannot be read, review again. Preserve the original source after failure or partial completion.

W13​

Upload a folder hierarchy​

Documentation: FULL. Before you start: Choose a bounded folder tree and the intended DAM parent.

Procedure. Choose Upload Folder. Wait for inventory to enumerate names, counts and dependencies. Inspect transformed repository names and per-item conflicts. Approve the plan, then track successful, failed and pending children separately.

Expected result. Parent/child relationships are preserved by the reviewed hierarchy. Partial success does not mean the entire tree is published.

Cancel, errors and recovery. Cancel stops further accepted work according to its actual state; it does not remove completed remote siblings or source files. Do not recursively ingest cache directories or follow external reparse points.

W14​

Upload saved changes and inspect versions​

Documentation: FULL. Before you start: Have an eligible locally edited generation and a current remote baseline.

Procedure. Open Edited locally, select the saved assets and choose Upload Changes. Review the exact generation and any supported version label/comment. Track binary commit separately from server processing. Inspect the history receipt or qualified AEM history surface; check-in is a separate dependent operation.

Expected result. A later editor save remains dirty even if the earlier upload succeeds. Processing or check-in failure can coexist with a successful binary commit.

Cancel, errors and recovery. If the remote outcome is unknown, inspect the original operation before retrying. Do not blindly resend. Do not claim version preservation where the adapter has disabled it.

W15​

Resolve an existing-name collision​

Documentation: FULL. Before you start: Use the collision review for a specific import batch and destination.

Procedure. Compare the incoming source and existing remote target. Choose Keep Both to reserve a distinct safe name, or a separately qualified Replace/Create Version option. Inspect the scope of any apply-to-all choice. Approve the final preview or choose Cancel.

Expected result. Only the reviewed batch and eligible targets receive the selected policy; successful or uncertain siblings are not reset.

Cancel, errors and recovery. If a destination changes after review, stop and review again. Unsupported replace/version options stay disabled. Never use a force-overwrite workaround.
