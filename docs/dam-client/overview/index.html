DAM Client overview

AEM assets. Local, on your desktop. Sambafied DAM Client is a native Windows client being built to bring AEM Assets into the folders and desktop applications you already use.

Our goal is simple: open Windows Explorer, find an asset in its AEM work folder, and work with it in your usual application. For teams using several AEM environments, each connection should have its own clearly named folder, available side by side.

For a concrete open, edit, save and verify journey, read Desktop Experience.

Why build another AEM client?​

AEM manages the assets. Your everyday work often happens elsewhere: placing an image in a layout, opening a video in an editor, or finding a file from an application's Open dialog. Moving between the repository, downloads and desktop tools can interrupt that work. Working across several brands or AEM environments adds another question: which repository does this file belong to?

We are building Sambafied for people who want the Windows filesystem to be their everyday route into AEM. Its focus is familiar folders, clear destinations and less connection switching across desktop tasks.

What makes the approach different?​

Start in Windows Explorer​

The work folder is central to the experience. The desktop window provides connections, asset discovery and transfer status; the intended day-to-day workflow also reaches assets through Explorer and application file dialogs.

The Windows preview has exercised a bounded AEM folder tree in Explorer with originals downloaded when opened. The aim is to make assets available without downloading the entire repository first. Check your build's folder access and limits before relying on a particular application workflow.

Give each AEM environment its own home​

A team might use folders named Brand Studio, Production and Staging, each connected to a different AEM Author. The intended benefit is keeping the right assets within reach while making the destination of each file clear.

Named connections and explicit work-folder paths are already part of the model. The complete simultaneous multi-instance experience remains under development. See multiple AEM instances for examples and evaluation checks.

Keep local work and uploads clear​

Editing a local file and publishing a change to AEM are separate events. Sambafied's guides explain how to open an original, review local changes, upload deliberately and check transfer results. A local save alone is not confirmation that the server copy changed.

This clarity is part of the workflow we are building, rather than a claim that existing clients lack upload controls. See opening and editing and transfers.

How does it compare with existing options?​

OptionWhere the workflow startsSambafied's focus
Adobe AEM desktop appA dedicated asset browser with browse, search, open, edit and upload actions. It already connects AEM to desktop applications.Put a native Windows work folder at the centre of everyday access, with per-instance folders as a central product goal.
Adobe Asset LinkAccess to AEM assets from inside Photoshop, Illustrator and InDesign. Adobe recommends Asset Link for those in-application workflows.Provide a folder workflow across Windows applications, with compatibility evaluated for each application and task.
AEM in the browserWork directly in AEM's web interface and download files for desktop use when needed.Keep the connection between desktop work folders and their AEM destinations visible throughout local work.

Adobe's desktop app already has on-demand downloads, and its v3 release notes describe automatic uploads of new files and collection synchronization. Those capabilities are not unique to Sambafied. Our distinction is the Explorer-first workflow and the goal of simultaneous, separate folders for different AEM instances. Read the detailed Adobe desktop app context for the server-switching comparison.

What can I try today?​

Sambafied is a Windows development preview. Start with a small test asset and the instructions supplied for your beta build. Bounded local AEM and Explorer scenarios have been exercised; this is not a claim of production readiness or a supported Windows/AEM compatibility matrix.

AEM on-premises and AEM as a Cloud Service are both in scope. Each environment and sign-in method needs its own testing. Simultaneous connections, offline work, conflict recovery, uploads and creative-application workflows still need build-specific confirmation. See readiness and limits.

Want to help shape the client? Become a beta tester, or open the desktop user guide for installation, connections and asset tasks.
